Rebuilt as a true cohort funnel — this replaces the earlier weekly-event-volume version, which was wrong. The row for each week is a fixed group of riders: everyone whose Lead stage (real or cascade-backfilled) falls in that week. Every number after that is “how many of that exact same group have ever reached this stage, as of today” — not a separate independent count for a different set of people in a different week. Because reached_installed ⇒ reached_lead, reached_kyc_done ⇒ reached_installed, etc. always holds per rider in the confirmed cascade, each column is guaranteed to be ≤ the one before it. Nothing here can read over 100% or increase step to step — if it does, that's a bug, not a data quirk. Totals reconcile exactly with the KPI tile above and across cohorts below: Lead 26,438, Installed 25,030, KYC initiated 15,424, KYC done 11,706, Onboarded 8,349, Activated 2,433. If the KPI cards above show a smaller Lead number than this, check the Week range picker at the top — it filters the whole page, and a narrowed range (e.g. starting mid-year) will legitimately show fewer riders than the all-time total quoted here.

Weekly Rider Mix — New / Retained / Resurrected vs Churned

Active = delivered ≥1 order that week. New = first-ever active week. Resurrected = returned after missing >2 weeks (matches the existing Reactivated flag). Churned(W) = active in W−1, not active in W.

Mix detail — absolute & %

Avg active days/week = stickiness / part-timer signal. WAR = distinct riders active (≥1 delivered order) at any point in the week. For each rider active that week, count how many distinct days they were active, then average across all of that week's active riders — a number from 0–7. Low (1–2 days) means the week's active pool is mostly showing up once or twice and gone — part-time / occasional gig behaviour. High (5–7 days) means most of that week's active riders are showing up nearly every day — full-time-like behaviour. Computed as (avg daily distinct riders ÷ WAR) × 7, which for a complete week is exactly total rider-active-days ÷ WAR — the sum, not a percentage; normalizing by days-elapsed-so-far (rather than a flat 7) is what keeps partial weeks on the same 0–7 scale as full ones, though partial-week values are an extrapolated pace, not a completed count. Weeks with fewer than 7 days of order data are marked partial — this includes the first/last weeks in the data window (window starts/ends mid-week) and also 2026-07-13, which is missing 2026-07-16 entirely (0 riders delivered any order that day, and 0 orders were even created platform-wide that day — a real outage, not a data artifact; worth checking against an incident log). Read the trend off full weeks only.

DAR/WAR detail

Anchored on Active week — the same weekly-active population used in the Weekly Rider Mix tab (delivered ≥1 order that week), not an Onboarding or Activation cohort. Onboarded is not shown here: Onboarded(week) and Activated(week) are independently-dated volumes for different people in different weeks, so they don't nest inside a single row and were confusing side by side. W+0 in this table is the row's full active headcount for that week — it matches the “Active total” column in Weekly Rider Mix exactly (verified: 0 mismatches across all 8 weeks). W+k = of that exact same group of riders active in week W, how many are also active k weeks later — so this includes New + Retained + Resurrected riders as the base, not just newly-activated ones. Rider activity data (delivered_orders) only goes back to , so cohorts before that show blank cells — a data-availability gap, not zero activity. Grey/blank cells past the right edge simply haven't happened yet.
